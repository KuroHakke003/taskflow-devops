## Work Completed

### PostgreSQL backup and restore testing

- Inspected an earlier SQL dump and discovered that it contained no task records.
- Created test data through the TaskFlow API.
- Generated a fresh PostgreSQL dump using `pg_dump` from the PostgreSQL pod.
- Created separate `taskflow_restore_test` and `taskflow_restore_automated_test` databases to avoid modifying the original database.
- Restored the initial dump into `taskflow_restore_test`.
- Restored an automated backup into `taskflow_restore_automated_test`.
- Verified that all three task records were successfully restored in both test databases.

### Bash backup automation

- Created a backup directory:
  - `/home/kuro/backups/taskflow/postgres`
- Wrote a custom Bash script (`backup-taskflow.sh`) to automate database backups.
- Implemented:
  - Timestamp-based backup filenames.
  - Automatic backup directory creation.
  - PostgreSQL dump execution through `kubectl exec`.
  - Temporary file creation before finalizing a backup.
  - File validation using `test -s`.
  - Moving the temporary file into its final backup filename after validation.
  - Cleanup of temporary files using `trap` on script exit.
  - Success and error output.
  - Automatic removal of backups older than 7 days using `find`.
- Tested the script manually and verified that it generated a valid SQL dump containing the task records.
- Simulated a backup failure by using an incorrect PostgreSQL pod name.
- Verified that the script exited on failure, removed the temporary file and did not perform retention cleanup.

### Cron automation and troubleshooting

- Configured a Cron job to schedule database backups.
- Added output and error logging to `backup.log`.
- Initially attempted to run the backup through the user's Cron, but encountered a sudo authentication issue because Cron does not provide an interactive terminal.
- Verified that the K3s administrative kubeconfig is restricted to root.
- Switched the scheduled backup execution to root's Cron instead of weakening sudo permissions.
- Removed `sudo` from the backup script and used the absolute path to `kubectl`.
- Tested the root Cron job with a temporary every-minute schedule.
- Confirmed that the scheduled execution successfully generated backup files.
- Configured the backup schedule to run daily at 02:00.
- Observed that backup files generated by root are owned by root.

### Kubernetes rolling updates and rollback practice

- Inspected the TaskFlow API Deployment, ReplicaSets, Pods and rollout configuration.
- Practiced triggering a Deployment rollout through a Pod template annotation.
- Observed how a Pod template change creates a new ReplicaSet and Deployment revision.
- Simulated a failed deployment by changing the API image to a nonexistent tag.
- Observed `ImagePullBackOff` on the new Pod while the previous healthy Pods continued running.
- Inspected ReplicaSets to understand how Kubernetes manages old and new replicas during a failed rollout.
- Practiced rolling back a Deployment using `kubectl rollout undo`.
- Verified that the Deployment returned to the previously working image and that the application Pods recovered.
- Practiced a targeted rollback using `--to-revision`.
- Verified the selected revision, restored Pod template and successful rollout status.

### Readiness probe troubleshooting

- Inspected the original API readiness probe configuration.
- Intentionally misconfigured the readiness probe to point to a nonexistent endpoint (`/health/ready-broken`).
- Observed that the new Pod remained `Running` but was not `Ready`.
- Inspected Pod conditions and events using `kubectl describe pod`.
- Identified repeated HTTP 404 errors from the readiness probe.
- Verified that the container was not restarting and that the liveness probe remained unaffected.
- Observed that the old healthy API Pods remained available while the new Pod failed readiness checks.
- Repaired the readiness probe and restored the correct `/health/ready` endpoint.
- Confirmed that the Deployment successfully rolled out and all API Pods became Ready.

### HPA scaling investigation

- Investigated why the API Deployment temporarily had three replicas instead of the previously configured two.
- Inspected the HorizontalPodAutoscaler (`api-hpa`).
- Verified the scaling configuration:
  - Minimum replicas: `1`.
  - Maximum replicas: `3`.
  - CPU target utilization: `50%`.
  - Memory target utilization: `70%`.
- Identified that the HPA had recently scaled the Deployment to three replicas based on memory utilization.
- Inspected HPA conditions, events and current metrics.
- Investigated the `ScaleDownStabilized` condition and the scale-down stabilization mechanism.
- Verified that the HPA was no longer limited by `maxReplicas`.
- Checked Pod resource requests and confirmed:
  - CPU request: `100m`.
  - Memory request: `128Mi`.
- Monitored API Pod resource usage using `kubectl top pods`.
- Observed stable memory consumption of approximately `61–63Mi` per API Pod.
- Compared memory utilization against the HPA target and explored how the HPA replica calculation and rounding affect scaling decisions.
- Confirmed that all three API Pods remained healthy and Ready while the HPA continued managing replica count.
