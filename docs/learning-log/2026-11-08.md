## Work Completed

### 1. GitHub Actions — CI

- Configured a GitHub Actions workflow to run automatically on pushes and pull requests targeting `main`.
- Set up an Ubuntu runner and Python 3.12 environment.
- Configured a PostgreSQL 16 service container for automated tests.
- Added dependency installation and `pytest` execution.
- Configured a PostgreSQL health check using `pg_isready`.
- Verified that the CI workflow completes successfully.

### 2. GitHub Actions — CD

- Created a separate `cd.yml` workflow.
- Configured workflow permissions:
  - `contents: read`
  - `packages: write`
- Added a test job with PostgreSQL service container.
- Configured job dependencies using `needs: test`.
- Added a condition to allow image publishing only on pushes to `main`, preventing publishing during pull requests.
- Configured authentication to GitHub Container Registry using `docker/login-action@v3` and the automatically provided `GITHUB_TOKEN`.

### 3. Docker Image Build and Publishing

- Integrated `docker/build-push-action@v6`.
- Configured the repository root as the Docker build context.
- Enabled automatic image publishing with `push: true`.
- Configured two image tags:
  - `latest` — convenient reference to the latest published image.
  - Git commit SHA — identifies the exact source revision used for the build.
- Successfully built and published the TaskFlow Docker image to GHCR.

## Results

- Verified that the package is publicly available on GitHub.

## Key Concepts Learned

- Difference between Continuous Integration and Continuous Delivery.
- How GitHub Actions service containers provide temporary dependencies for automated tests.
- How workflow jobs depend on each other through `needs`.
- How job-level `if` conditions control when a job executes.
- How `GITHUB_TOKEN` authenticates workflows with GitHub services.
- Difference between building a Docker image and pushing it to a registry.
- Why immutable commit-based image tags are useful for identifying builds and rolling back.
