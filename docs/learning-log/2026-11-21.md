# Learning Log — 2026-11-21

## Kubernetes Security Hardening — TaskFlow

Today I worked on hardening the TaskFlow application running in my K3s cluster. I went through several security and operational improvements, starting with namespace isolation and application configuration, then container security, resource management, backup and restore, ServiceAccounts, RBAC principles, and network isolation.

---

### 1. Namespace Isolation

- Created and configured a dedicated Kubernetes namespace `taskflow` for the application.
- Organized TaskFlow resources within the dedicated namespace instead of relying on the default namespace.
- Used namespace-scoped resource management throughout the hardening process.

### 2. DATABASE_URL Configuration

- Verified how Kubernetes environment variable expansion works inside container specifications.
- Configured the `DATABASE_URL` environment variable using other environment variables.
- Learned how Kubernetes expands `$(VAR_NAME)` references in container environment variable values.
- Ensured that referenced variables are defined before `DATABASE_URL` to avoid incorrect expansion.
- Verified that the application could successfully connect to PostgreSQL using the updated configuration.

### 3. Dockerfile Hardening

- Modified the TaskFlow Dockerfile to run the application as a non-root user.
- Configured the application container to use UID/GID `999`.
- Verified the running container's identity using `id`.
- Confirmed that the application runs without root privileges.

### 4. Kubernetes SecurityContext

Configured security-related settings for the TaskFlow API Deployment:

- `runAsNonRoot: true` — prevents the container from running as root.
- `runAsUser: 999` — specifies the user ID.
- `runAsGroup: 999` — specifies the group ID.
- `allowPrivilegeEscalation: false` — prevents processes from gaining additional privileges.
- `capabilities.drop: ALL` — removes Linux capabilities from the container.

Verified that the Deployment rolled out successfully and the API Pods remained operational.

### 5. Resource Requests and Limits

Configured resource requests and limits for both application and database workloads.

**TaskFlow API:**

- CPU request: `100m`
- Memory request: `128Mi`
- CPU limit: `500m`
- Memory limit: `256Mi`

**PostgreSQL:**

- CPU request: `100m`
- Memory request: `128Mi`
- CPU limit: `500m`
- Memory limit: `512Mi`

Learned how resource requests and limits help Kubernetes schedule workloads and restrict resource consumption.

### 6. Horizontal Pod Autoscaler (HPA)

- Configured HPA for the TaskFlow API.
- Added CPU-based scaling with a target of `50%`.
- Added memory-based scaling with a target of `70%`.
- Configured a minimum of `1` replica and a maximum of `3` replicas.
- Verified that CPU and memory metrics were available.
- Confirmed that the HPA was operating with 2 API replicas.

### 7. PostgreSQL Backup and Restore

- Created a PostgreSQL backup from the Kubernetes database.
- Performed a restore test using a temporary PostgreSQL environment.
- Restored the database schema and the `tasks` table.
- Verified that the restored table existed and was owned by the expected database user.
- Confirmed that the restore operation completed successfully.

The backup contained an empty baseline database, so the restored `tasks` table contained `0` rows. The test verified the schema restoration process rather than recovery of populated production data.

### 8. ServiceAccount and Kubernetes Access Security

- Created a dedicated ServiceAccount named `taskflow-api`.
- Configured the ServiceAccount with `automountServiceAccountToken: false`.
- Connected the ServiceAccount to the TaskFlow API Deployment using `serviceAccountName`.
- Verified that the Kubernetes ServiceAccount token was not automatically mounted into the API container.
- Confirmed that the application does not require Kubernetes API permissions for its current functionality.
- Applied the least-privilege principle by avoiding unnecessary Role and RoleBinding permissions.

### 9. PostgreSQL NetworkPolicy

Created `k8s/networkpolicy-postgres.yaml`.

- Targeted PostgreSQL Pods using `app=postgres`.
- Restricted incoming traffic to TCP port `5432`.
- Allowed incoming connections only from Pods labeled `app=taskflow-api` within the same namespace.
- Applied the NetworkPolicy to the cluster.
- Verified that the TaskFlow API could still connect to PostgreSQL.
- Created a temporary test Pod and attempted to connect to the database.
- Confirmed that the unauthorized test Pod could not connect to PostgreSQL.

This verified that database access was restricted to the intended application workload.

### 10. API NetworkPolicy

Created `k8s/networkpolicy-api.yaml`.

- Targeted API Pods using `app=taskflow-api`.
- Restricted incoming traffic to TCP port `8000`.
- Allowed incoming connections from Pods within the same namespace using an empty `podSelector`.
- Applied the NetworkPolicy and verified its configuration.

The policy restricts API ingress to Pods within the `taskflow` namespace, while leaving egress traffic unrestricted.

### 11. NetworkPolicy Testing and Verification

Performed connectivity tests to verify the API NetworkPolicy.

**Internal namespace test:**

- Created a temporary Pod inside the `taskflow` namespace.
- Connected to the API using the `taskflow-api` Service.
- Verified that the API returned:

  `{"status":"ready","database":"reachable"}`

- Confirmed that internal namespace communication was allowed.

**External namespace test:**

- Created a temporary namespace named `net-test`.
- Created a test Pod inside the namespace.
- Attempted to connect to the API using its Kubernetes Service DNS name.
- Received `Connection refused`.

**Direct Pod IP test:**

- Retrieved the API Pod IP addresses.
- Attempted to connect directly to an API Pod using its IP address, bypassing the Service.
- Received `Connection refused` again.

These tests confirmed that connections from the external test namespace were not accepted, both through the Service and directly through the API Pod IP.

- Removed the temporary test Pod in `taskflow`.
- Removed the temporary `net-test` namespace.

### 12. Final Cluster Verification

Verified the current Kubernetes resources using:

`kubectl get deployments,statefulsets,services,hpa,pvc -n taskflow`

Final state:

- **TaskFlow API Deployment:** `2/2` replicas ready.
- **PostgreSQL StatefulSet:** `1/1` ready.
- **API Service:** `taskflow-api`, ClusterIP, port `8000`.
- **Database Service:** `db`, ClusterIP, port `5432`.
- **PostgreSQL Headless Service:** `postgres-headless`.
- **HPA:** `api-hpa`, CPU and memory metrics available, 2 current replicas, scaling range of 1–3.
- **PostgreSQL PVC:** `postgres-pvc`, `Bound`, 2Gi, `local-path` storage class.

Verified that the application and database remained operational after applying the security configurations.
