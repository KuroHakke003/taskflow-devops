## Kubernetes CI/CD Automation

Today I implemented and successfully tested an automated CI/CD pipeline for TaskFlow using GitHub Actions, GHCR, Tailscale, SSH and K3s.

### CI pipeline

- Consolidated the workflows into a single `cd.yml` workflow and removed the duplicate `ci.yml`.
- Configured GitHub Actions to run tests on pushes and pull requests targeting `main`.
- Configured PostgreSQL 16 as a CI service container.
- Set up Python 3.12 and dependency installation.
- Automated test execution using `pytest`.

### Docker image build and publishing

- Configured an automated Docker image build after successful tests.
- Published images to GitHub Container Registry (GHCR).
- Configured image tags using both `latest` and the Git commit SHA.
- Restricted image publishing to pushes to the `main` branch.

### Secure deployment connectivity

- Configured a Tailscale OAuth client for GitHub Actions.
- Created and assigned the `tag:ci` tag for the CI runner.
- Added the Tailscale OAuth credentials to GitHub Actions Secrets.
- Connected the ephemeral GitHub Actions runner to the Tailscale network.
- Configured SSH deployment using a dedicated `taskflow-deploy` user instead of the regular server account.
- Generated a dedicated SSH key pair for GitHub Actions and stored the private key in GitHub Actions Secrets.
- Restricted the deployment SSH key using `authorized_keys` forced-command configuration and an SSH wrapper.
- Created a restricted sudo rule allowing the deployment user to execute only the dedicated deployment script.
- Configured SSH host fingerprint verification in the workflow.
- Used the server's SSH port 2222 for the deployment connection.

### Deployment automation

- Created `/usr/local/bin/taskflow-deploy` to automate Kubernetes image updates.
- Restricted the deployment script to accept a valid 40-character Git commit SHA.
- Automated image updates using `kubectl set image`.
- Configured the script to wait for deployment completion using `kubectl rollout status`.
- Connected the deployment process to the existing K3s cluster without manually executing the rollout.

### Troubleshooting

During the first deployment attempts, I encountered and resolved several issues:

- **SSH port mismatch:** The server was listening on port 2222 rather than the default port 22. Updated `ssh-keyscan` and SSH connection commands.
- **kubectl path:** The deployment script initially referenced `/usr/bin/kubectl`, which did not exist. Updated the script to use `/usr/local/bin/kubectl`, the K3s kubectl symlink.
- **Container name mismatch:** The deployment script initially referenced the container as `api`. Updated it to `taskflow-api`, matching the actual container name in the Kubernetes Deployment.

### Successful deployment verification

The GitHub Actions pipeline completed successfully, including the deployment job.

Verified the live Kubernetes deployment:

- `taskflow-api` Deployment — 2/2 replicas ready.
- Both API Pods — Running and Ready (1/1).
- PostgreSQL Pod — Running and Ready (1/1).
- Both API Pods were recreated during the deployment and successfully started.

### Key takeaways

- A CI/CD pipeline can automate testing, image publishing and Kubernetes deployments as a single workflow.
- Git commit SHA tags allow deployments to target specific image versions rather than relying exclusively on mutable tags such as `latest`.
- Tailscale can provide private connectivity between GitHub Actions runners and a self-hosted Kubernetes environment without relying on public SSH access.
- SSH forced commands, a dedicated deploy user and restricted sudo permissions help limit the scope of deployment access.
- Deployment scripts must use the actual Kubernetes container names and correct executable paths.
- `kubectl rollout status` allows automated pipelines to verify that a deployment has completed successfully.
- Troubleshooting real deployment failures helped me understand the relationship between GitHub Actions, SSH, Linux permissions, Tailscale, container images and Kubernetes Deployments.

Today I completed the first fully automated CI/CD deployment of TaskFlow to my K3s cluster.
