### Linux Process Troubleshooting

- Stopped the K3s service to prevent the problematic Kubernetes workload from continuing to consume CPU resources.
- Discovered that CPU usage remained critically high even after stopping K3s.
- Used `htop` and sorted processes by CPU consumption.
- Identified four abnormal `gosu postgres` processes, each consuming approximately 200% CPU.
- Investigated their parent process using `ps`.
- Discovered that all four processes shared the same parent PID (`90228`).
- Identified the parent as `containerd-shim-runc-v2`, associated with the Kubernetes container runtime.
- Determined that the affected processes were still running after K3s had been stopped.
- Terminated the four runaway processes using `kill`.

### CPU Recovery

After terminating the four processes, CPU usage dropped dramatically:

This confirmed that the four runaway processes were responsible for the immediate CPU overload.

## Problems & Troubleshooting

### PostgreSQL startup failure

The PostgreSQL container entered the `Running` state, but the database itself did not become available.

Observed symptoms:

- Container status: `1/1 Running`.
- Restart count: 0.
- PostgreSQL logs were empty.
- `pg_isready` returned `no response`.
- PostgreSQL data directory was empty.
- The expected PostgreSQL server process did not start correctly.

The exact underlying cause of the PostgreSQL startup failure remains unidentified.

### Runaway gosu processes

Four `gosu postgres` processes were consuming approximately 200% CPU each.

The processes included:

- PostgreSQL container entrypoint.
- A PostgreSQL data directory write-permission check.
- `gosu postgres id`.
- `gosu postgres true`.

All four processes had the same parent, a Kubernetes `containerd-shim-runc-v2` process.

Even after stopping K3s, these processes continued consuming CPU until manually terminated.

After terminating them, CPU usage immediately returned to normal levels.

The reason these processes became stuck still requires investigation.

## What I Learned

- A Kubernetes Pod can report `Running` even when the application inside the container is not functioning correctly.
- Container readiness and actual application availability are different things.
- `kubectl top pod` helps identify resource consumption at the Pod level.
- `htop` can be used to inspect and sort processes by CPU consumption.
- `ps` can reveal process IDs, parent process IDs, execution states, and elapsed time.
- Linux processes form parent-child relationships.
- `gosu` is used to execute commands under a different user.
- `containerd-shim-runc-v2` manages container processes.
- Stopping a Kubernetes service does not necessarily guarantee that every associated container process has terminated.
- Grafana dashboards help visualize infrastructure resource usage.
- Prometheus and Alertmanager can detect abnormal resource consumption and deliver notifications.
- Monitoring alerts help identify incidents, while Linux process inspection helps locate their source.
