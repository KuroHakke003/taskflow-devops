## 1. Docker Compose — TaskFlow API HTTP 500 Incident

### Initial Symptoms

The TaskFlow API returned:

`HTTP 500 Internal Server Error`

when sending requests to the `/tasks` endpoint.

The Docker Compose services appeared to be running normally, and PostgreSQL was reported as healthy.

This suggested that the failure might be inside the application rather than caused by the database container being unavailable.

### Investigation

- Inspected Docker Compose service status.
- Checked API container logs.
- Examined the Python traceback generated during API requests.
- Traced the exception to the Prometheus FastAPI instrumentation middleware.

The important error was:

`AttributeError: '_IncludedRouter' object has no attribute 'path'`

The exception occurred inside `prometheus-fastapi-instrumentator` version 7.1.0.

This indicated a compatibility problem with the FastAPI routing implementation in the installed dependency set.

### Root Cause and Fix

The problem was caused by an incompatible version of `prometheus-fastapi-instrumentator`.

Updated the dependency constraint in `requirements.txt`:

- Previous: `prometheus-fastapi-instrumentator>=7.0,<8.0`
- Updated: `prometheus-fastapi-instrumentator>=8.0.1,<9.0`

Checked dependency resolution using:

`pip install --dry-run -r requirements.txt`

The resolver selected:

- `prometheus-fastapi-instrumentator 8.1.0`
- `FastAPI 0.163.2`
- `Starlette 1.10.0`

This was an application middleware compatibility issue. PostgreSQL itself was not identified as the cause of this HTTP 500 error.

## 2. Kubernetes — PostgreSQL Startup Failure

### Environment

Continued troubleshooting the TaskFlow Kubernetes environment running on a single-node K3s cluster.

The application was deployed in the `taskflow` namespace.

Main Kubernetes resources involved:

| Resource | Name |
|---|---|
| Namespace | `taskflow` |
| API Deployment | `taskflow-api` |
| PostgreSQL Deployment | `postgres` |
| PostgreSQL Service | `db` |
| Kubernetes Secret | `postgres-secret` |
| PersistentVolumeClaim | `postgres-pvc` |

PostgreSQL used the image:

`postgres:16-bookworm`

Persistent storage was mounted at:

`/var/lib/postgresql/data`

The database credentials were supplied through the Kubernetes Secret rather than being hardcoded into the Deployment manifest.

### Initial Symptoms

The PostgreSQL Pod repeatedly appeared in the `Running` state, but the database was not actually accepting connections.

Observed behavior:

- PostgreSQL Pod showed `1/1 Running`.
- The container had multiple restarts.
- The API Pod entered `CrashLoopBackOff`.
- API startup failed because PostgreSQL was unavailable.
- `pg_isready` returned `no response`.
- PostgreSQL logs were empty.
- The PostgreSQL data directory appeared empty during the investigation.
- The PostgreSQL server process did not start correctly.

This demonstrated that a container can be running without the application inside it being operational.

### Inspecting Kubernetes Resources

Used:

`kubectl get pods -n taskflow -o wide`

to inspect Pod states, restart counts, IP addresses, and node placement.

Used:

`kubectl describe pod -n taskflow -l app=postgres`

to inspect the PostgreSQL Pod in detail.

The description showed:

- The PostgreSQL container was using `postgres:16-bookworm`.
- The PVC was mounted read-write at `/var/lib/postgresql/data`.
- The container had exited previously with exit code 2.
- The previous container had run for approximately 20 minutes before terminating.
- Kubernetes recorded repeated container creation and startup events.
- The Pod had experienced `SandboxChanged` and `BackOff` events.

The PVC remained attached to the workload and was not deleted during troubleshooting.

### Inspecting the Container Runtime with crictl

Since K3s uses containerd rather than the regular Docker Engine for Kubernetes workloads, used `crictl` to inspect the underlying containers.

Command:

`sudo crictl ps -a --name postgres`

This revealed both a running PostgreSQL container and a previously exited container.

Inspected the exited container:

`sudo crictl inspect <container-id>`

Important findings:

- Container state: `CONTAINER_EXITED`.
- Exit code: `2`.
- Reason: `Error`.
- The container had been running for approximately 20 minutes.
- Its termination message was empty.
- Its logs were empty.
- The container used the expected PostgreSQL image and PVC mount.

This helped establish that the failure was occurring during container startup, before PostgreSQL became available.

### Inspecting Container Logs and Termination Information

Checked the previous container logs using:

`kubectl logs -n taskflow <postgres-pod> --previous`

The output was empty.

Also inspected the container's log file and termination message directly on the host.

Both were empty.

Because ordinary application logs did not explain the failure, the investigation moved to the Linux process and kernel level.

## 3. Kubernetes — Abnormal CPU Consumption and gosu Investigation

### Previous CPU Incident

During the earlier investigation on November 16:

- Stopping the K3s service did not immediately stop all associated container processes.
- CPU consumption remained abnormally high.
- Used `htop` to identify processes consuming CPU.
- Found four `gosu postgres` processes consuming approximately 200% CPU each.
- Used `ps` to inspect their parent processes.
- Identified `containerd-shim-runc-v2` as their common parent.
- Terminating those runaway processes caused CPU consumption to drop dramatically.

This established that the abnormal CPU usage was associated with stuck PostgreSQL container startup processes.

However, the underlying cause was not yet known.

### Investigating the Process on November 18

After rebooting the VM, the Kubernetes PostgreSQL issue returned.

The K3s service started automatically, and the PostgreSQL container again became stuck.

Inspected the process using:

`ps`

and:

`/proc/<PID>/status`

The problematic process was:

`gosu`

Important observations:

- It was running as the container's PID 1.
- Its parent process was `containerd-shim-runc-v2`.
- It was actively consuming approximately one CPU core.
- It had five threads.
- Its main thread was in the running state.
- The other threads were mostly sleeping.
- The process was not waiting in a normal blocking kernel wait channel.
- The container process had not successfully completed its startup sequence.

The host PID was different from the PID inside the container. `/proc/<PID>/status` showed:

`NSpid: 13534 1`

This demonstrated the relationship between the host PID namespace and the container PID namespace.

### Using top and strace

Used:

`top -H -p <PID>`

to inspect CPU usage at the thread level.

This showed that the main `gosu` thread was consuming nearly all of the CPU allocated to one core.

Used:

`strace -f -p <PID>`

to observe system calls made by the process.

The main thread repeatedly executed:

`sched_yield() = 0`

The other threads were waiting in `futex()`.

Then used:

`strace -k -p <PID>`

to inspect the call stack associated with the repeated system calls.

The stack repeatedly showed:

- `runtime.osyield`
- `syscall.AllThreadsSyscall`
- `syscall.Setgid`
- `main.SetupUser`
- `main.main`
- `runtime.main`

This was a major breakthrough.

It showed that `gosu` was stuck while trying to change the process group identity through Go's `Setgid` implementation.

The Go runtime was waiting for its threads to participate in a process-wide system call.

A further trace using:

`strace -f -e trace=setgid,setgroups -p <PID>`

did not show the expected `setgid` or `setgroups` calls before the timeout.

This supported the conclusion that the process was stuck before successfully completing the credential change.

## 4. Kernel Logs and AppArmor Investigation

### Inspecting Kernel Messages

Since the process was stuck inside a system-level operation, inspected the kernel journal for the period when PostgreSQL was failing.

Command:

`sudo journalctl -k --since "2026-11-18 06:00:00" --until "2026-11-18 06:30:00" --no-pager`

The output contained multiple AppArmor audit messages.

The important messages included:

- `apparmor="DENIED"`
- `operation="signal"`
- `profile="cri-containerd.apparmor.d"`
- `comm="gosu"`
- `requested_mask="send"`
- `denied_mask="send"`

The denied signals included:

- `SIGTERM`
- `SIGRTMIN+1`

These messages occurred around the same time as the PostgreSQL container failures and the creation of new stuck `gosu` processes.

The kernel journal also contained CPU latency warnings, including:

- `hrtimer: interrupt took ...`
- `workqueue: blk_mq_run_work_fn hogged CPU for >10000us`

These warnings indicated system-level CPU and scheduling pressure during the incident, but they were not treated as the primary root cause.

### Inspecting AppArmor Status

Used:

`sudo aa-status`

Confirmed that:

- AppArmor was enabled.
- The system had multiple profiles loaded in enforce mode.
- `cri-containerd.apparmor.d` was loaded in enforce mode.
- The problematic `gosu` process was running under the containerd AppArmor profile with a stacked unconfined label.

The process label was:

`cri-containerd.apparmor.d//&unconfined`

This was important because the profile's signal permissions did not properly account for communication with processes carrying this stacked label.

### Understanding the Root Cause

The investigation matched a known containerd/AppArmor compatibility issue affecting systems using restricted unconfined AppArmor profiles.

The containerd profile allowed signals to the regular profile name:

`cri-containerd.apparmor.d`

However, it did not correctly allow the corresponding stacked peer label:

`cri-containerd.apparmor.d//&unconfined`

As a result, AppArmor denied signals needed for communication between container processes.

The Go runtime uses signals to coordinate operations such as changing group credentials across all threads.

When `gosu` attempted to execute `Setgid`, the required thread coordination could not complete correctly.

The process repeatedly yielded CPU through `sched_yield()` instead of finishing the operation.

This explained the complete chain of symptoms:

1. AppArmor denied required signals.
2. The Go runtime could not complete its process-wide credential operation.
3. `gosu` became stuck in its startup sequence.
4. The PostgreSQL entrypoint could not finish initialization.
5. PostgreSQL never started accepting connections.
6. `pg_isready` returned `no response`.
7. The TaskFlow API could not connect to the database and entered `CrashLoopBackOff`.
8. Stuck container processes caused abnormal CPU consumption.

## 5. AppArmor Fix

### Updating the Containerd AppArmor Profile

Instead of disabling AppArmor globally, created a local profile override:

`/etc/apparmor.d/cri-containerd.apparmor.d`

The profile retained the existing containerd restrictions and added explicit permissions for the stacked unconfined peer.

The important additional rules were:

`signal (send,receive) peer=cri-containerd.apparmor.d//&unconfined,`

`ptrace (trace,tracedby,read,readby) peer=cri-containerd.apparmor.d//&unconfined,`

These rules allow the required signal and ptrace interactions with processes carrying the stacked label.

The profile was loaded using:

`sudo apparmor_parser -r /etc/apparmor.d/cri-containerd.apparmor.d`

The command completed without reporting an error.

AppArmor remained enabled and the profile remained in enforce mode.

### Why This Fix Was Important

The solution addressed the missing permissions in the specific containerd AppArmor profile.

It avoided globally disabling AppArmor or removing the host's security enforcement.

The fix targeted the actual cause discovered through kernel audit logs and process tracing.

## 6. Kubernetes Recovery

After loading the updated AppArmor profile, the existing PostgreSQL process was still not accepting connections.

The PostgreSQL Deployment was restarted:

`sudo kubectl rollout restart deployment/postgres -n taskflow`

This caused Kubernetes to recreate the PostgreSQL Pod using the updated AppArmor policy.

The TaskFlow API Deployment was also restarted:

`sudo kubectl rollout restart deployment/taskflow-api -n taskflow`

This ensured that the API started again after PostgreSQL had recovered.

## What I Learned

### Docker and Application Troubleshooting

- A healthy container does not guarantee that every application request will succeed.
- HTTP 500 errors can originate in middleware before a request reaches its API route or database.
- FastAPI, Starlette, and instrumentation libraries must use compatible versions.
- Dependency constraints help prevent incompatible package upgrades.
- `pip install --dry-run` can inspect dependency resolution without installing packages.

### Kubernetes

- A Pod can report `Running` while the application inside it is not functioning.
- Pod readiness, container state, and actual application availability are different concepts.
- `kubectl get pods` provides a quick overview of workload state.
- `kubectl describe pod` exposes container states, restart history, mounts, environment references, and Kubernetes events.
- `kubectl logs --previous` can retrieve logs from a previous container instance.
- Kubernetes uses containerd through the CRI interface in this K3s environment.
- `crictl` provides lower-level access to container runtime information.
- A Deployment restart recreates Pods without intentionally deleting the associated PVC.
- PersistentVolumeClaims must be protected during troubleshooting.

### Linux Process Debugging

- `ps` can reveal process IDs, parent process IDs, states, and elapsed time.
- `/proc/<PID>/status` exposes process information, including thread count and namespace PID mappings.
- `top -H` displays CPU usage per thread.
- `strace` can reveal which system calls a process is executing.
- `strace -k` can expose call stacks associated with system calls.
- Repeated `sched_yield()` calls can indicate a process actively yielding CPU rather than waiting for a normal blocking operation.
- `futex()` is used for synchronization between threads.
- Linux processes can remain alive even after the service that originally created them has been stopped.

### AppArmor and Container Runtime

- AppArmor enforces security policies on processes.
- AppArmor can restrict communication through signals, not just filesystem access.
- Containerd uses an AppArmor profile for its containers.
- Stacked AppArmor labels can affect how peer permissions are matched.
- Go runtime operations such as `Setgid` can require coordination between multiple threads.
- A denied signal can prevent a container entrypoint from completing its startup sequence.
- Kernel audit logs can reveal security denials that are not visible in application logs.
- `apparmor_parser -r` replaces an already loaded AppArmor profile.
